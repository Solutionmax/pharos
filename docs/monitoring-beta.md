# Monitoring, remote backups and passkeys

HTTP monitors capture the leaf certificate expiry from the same verified, pinned HTTP request. Certificates with 14 days or less show a renewal warning in the administration form; certificates with 3 days or less set Performance issues. Expired, untrusted and hostname-invalid certificates fail the check. Redirects are not followed. A response is capped at 1 MiB, compression is disabled, and optional expected text must occur exactly in the response. Targets must be HTTP(S), a TCP host/port, or a DNS record name. DNS supports A, AAAA, CNAME, MX and TXT; MX expectations are `priority hostname`, and split TXT character strings are joined. IPv6 comparisons use packed addresses. The 24-hour latency chart groups measured data in 288 five-minute buckets and leaves missing buckets empty. Public charts are opt-in per component and show no target or check message.

## Probe locations

A page administrator creates a location and selects which checks it may run. Download the credential file immediately; it can be downloaded once. On a separate Pharos installation, put its `PHAROS_PROBE_HUB` and `PHAROS_PROBE_TOKEN` values in the private `.env`, then schedule `php artisan pharos:probe-remote` every minute (or use the ordinary Pharos scheduler, which includes this command). Hub requests require HTTPS. An installation administrator may explicitly approve a private hub host using the existing internal-host allow list. Neither a page editor nor an API token can configure a hub URL.

`GET /api/v1/probe/jobs` returns at most 100 assigned enabled checks and a two-minute job identifier. `POST /api/v1/probe/results` accepts only `job`, boolean `ok`, and optional bounded `latency_ms`. The server binds the job to its location and check, records the server receipt time, and consumes each identifier once. The location token has no authority over component CRUD, other pages or other checks. Removing or disabling a location revokes it. Credentials are bound to the issuing user and require that user’s current page-admin authority and a nonarchived owning page on every poll/result. Unpublished pages remain monitorable. Unattributable legacy locations are retained but disabled during migration; a page administrator must recreate their credential. Fresh samples from revoked credentials cannot vote healthy.

The local probe counts as one location. With two remote locations, two healthy votes out of three mean healthy even when the third fails. Results older than twice the interval (minimum 120 seconds) are stale and do not vote. A strict majority of configured enabled locations is required; insufficient fresh results show Performance issues without manufacturing healthy uptime or opening an outage incident. The administration location page shows stale/missing counts and each location's last connection. Results are retained two days; jobs are pruned after a day.

## Web scheduler

Ordinary hosting cron remains preferred: `php artisan schedule:run` every minute. A global administrator can enable the external fallback on Scheduler and backups after configuring a random token of at least 32 characters as `PHAROS_WEB_CRON_TOKEN` in the private environment. Both `POST /api/cron` and `GET /cron/run` accept an `Authorization: Bearer <credential>` header. URL-only cron services must support configuring that header. Query-string credentials are deliberately rejected because web servers and external services often retain URLs in access logs. The UI never displays the token. The fallback uses constant-time authentication, rate limits and a shared five-minute scheduler lock; scheduled jobs retain their existing overlap locks. Disable the fallback or rotate the environment token to revoke access.

## Remote backups

Only installation administrators can add, run or remove destinations. S3 credentials and SFTP passwords are encrypted using Laravel's application key and never redisplayed, serialized or flashed after validation. S3 requires HTTPS, uses private objects and SigV4 authentication, and resolves/vets/pins the destination for every request including streamed reads. Redirects and TLS verification overrides are prohibited. For an intentionally private storage endpoint the administrator must select Allow this destination on a private network. Loopback, this machine and metadata/link-local addresses remain prohibited. SFTP pins the vetted address and requires a complete verified SHA256 or SHA512 SSH host fingerprint (OpenSSH SHA256 form, raw or colon-delimited hexadecimal, and base64 are supported). Invalid or missing persisted fingerprints fail closed before a connection. Verify that fingerprint through a trusted channel; do not accept one from an untrusted first connection.

`php artisan pharos:backup-remote` runs daily at 02:45 through the normal scheduler; Back up now performs the same delivery. For SQLite it uses the native SQLite online backup API and checks integrity, including data still in WAL. This requires PHP's sqlite3 and zip extensions. MySQL snapshots use installed `mysqldump --single-transaction --quick`; the credentials travel through a temporary private config file and are removed afterward. Transactional database tables are required for a consistent MySQL dump; the external MySQL backup path has not been acceptance-tested in this beta environment. Application files, `.env` (APP_KEY), migrations and public uploads are included; dependencies, git data, caches, sessions, logs and older backups are excluded. Each upload is downloaded and SHA256 checked. Status records the last attempt, success and a generic failure message. Local temporary archives are deleted in all delivery paths. Configure destination lifecycle/retention separately; Pharos does not delete remote historical backups.

The archive contains account data and credentials: keep storage private. To restore, stop writes, restore files and `.env`, restore `database/database.sqlite` or import `database/database.sql`, reinstall dependencies from `composer.lock`, create writable storage/cache directories and restart the scheduler. Shared-hosting installations with a separate public directory back up the actual configured public_path under one public/ archive prefix; stale base/public files are excluded. BACKUP-LAYOUT.json records the source mapping. Restore public/ into the current configured document root, not blindly into the application tree; rebuild the storage symlink and adjust .pharos-public if moving hosts. Public .env files and symlinks are excluded. Preserve the original APP_KEY; it decrypts stored destination credentials and TOTP secrets.

## Passkeys

Registration, list and password-confirmed removal are available on Your profile. Sign in with a passkey uses a discoverable credential, so it does not ask for an email or disclose whether an account exists. Registration requires the current account password. Device verification and user presence are required; the maintained `lbuchs/webauthn` library checks challenge, RP hash, origin, signatures and signature counters. Pharos additionally checks the exact configured origin (including scheme/port), rejects cross-origin ceremonies, binds the returned user handle to the credential's account and atomically consumes an expiring database challenge. Existing enabled TOTP remains a separate required sign-in step; passkeys do not satisfy or disable an administrator's TOTP enrollment requirement.

Configure `PHAROS_WEBAUTHN_ORIGIN` to the exact administrator HTTPS origin, defaulting to APP_URL. RP ID is its hostname. HTTPS with a hostname is required outside localhost. IP origins are not valid WebAuthn RP IDs (W3C §5.1.3/§5.1.4 allow only the domain form of host); an HTTPS IP address alone is insufficient. The existing HTTP LAN site may remain accessible, but it cannot register/use passkeys: provide an HTTPS LAN hostname/certificate for the administrator origin, for example `https://pharos-beta.home.arpa`, and set APP_URL to that administrator origin because central administration deliberately rejects other hosts. A Chromium insecure-origin-as-secure override alone does not bypass the server's HTTPS origin verification. Changing the RP hostname requires registering credentials for the new RP. Backup your existing account recovery path before removing a device.
