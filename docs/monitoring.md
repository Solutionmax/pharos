# Monitoring, remote backups and passkeys

HTTP monitors capture the leaf certificate expiry from the same verified, pinned HTTP request. Certificates with 14 days or less show a renewal warning in the administration form; certificates with 3 days or less set Performance issues. Expired, untrusted and hostname-invalid certificates fail the check. Redirects are not followed. A response is capped at 1 MiB, compression is disabled, and optional expected text must occur exactly in the response. Targets must be HTTP(S), a TCP host/port, or a DNS record name. DNS supports A, AAAA, CNAME, MX and TXT; MX expectations are `priority hostname`, and split TXT character strings are joined. IPv6 comparisons use packed addresses. The 24-hour latency chart groups measured data in 288 five-minute buckets and leaves missing buckets empty. Public charts are opt-in per component and show no target or check message.

## Private network targets

A check (HTTP or TCP) or a notification destination on a private network turns the server into a scanner for its own LAN in the wrong hands: a TCP check answers which ports are open, a keyword check reads a page nobody outside can see. So since 1.2.0:

- An installation administrator may always save private targets (RFC 1918, carrier grade NAT and Tailscale, IPv6 unique local and the like).
- A page editor or page administrator may only when **Settings → General → Let page editors check private network addresses** is on. It is off on a new installation. An installation updated from 1.1 has it on when one of its checks or destinations already reached a private address at the time of the update, so nothing stops working.
- The rule is applied when the target is saved and again on every run and delivery, so a name that later resolves to a private address gets no request. A target an installation administrator saved keeps working whatever the setting says; an editor who changes it takes that over. Remote probe locations receive the same decision from the hub with each job.
- This machine and link local (cloud metadata) stay refused for everyone.

Turning the setting off stops private checks and destinations that an editor saved. To keep one, open it and save it again as an installation administrator.

## Probe locations

A page administrator creates a location and selects which checks it may run. Download the credential file immediately; it can be downloaded once. On a separate Pharos installation, put its `PHAROS_PROBE_HUB` and `PHAROS_PROBE_TOKEN` values in the private `.env`, then schedule `php artisan pharos:probe-remote` every minute (or use the ordinary Pharos scheduler, which includes this command). Hub requests require HTTPS. An installation administrator may explicitly approve a private hub host using the existing internal-host allow list. Neither a page editor nor an API token can configure a hub URL.

`GET /api/v1/probe/jobs` fairly selects one due job from at most 100 assigned enabled checks and creates its two-minute identifier only when a worker is ready. Completed jobs rotate behind older due work; pending unexpired jobs are not duplicated. The native worker claims at most 20 jobs per run within a 50-second budget, with 6-second hub requests and the configured check timeout (at most 30 seconds). It reserves enough time for one worst-case check plus result delivery before each claim. Probe bodies are capped at 16 KiB before global JSON parsing; job responses at 256 KiB and result replies at 16 KiB during transfer. `POST /api/v1/probe/results` accepts only `job`, boolean `ok`, and optional bounded `latency_ms`. The server binds the job to its location and check, records the server receipt time, and consumes each identifier once. The location token has no authority over component CRUD, other pages or other checks. Removing or disabling a location revokes it. Credentials are bound to the issuing user and require that user’s current page-admin authority and a nonarchived owning page on every poll/result. Unpublished pages remain monitorable. Unattributable legacy locations are retained but disabled during migration; a page administrator must recreate their credential. Fresh samples from revoked credentials cannot vote healthy.

The local probe counts as one location. With two remote locations, two healthy votes out of three mean healthy even when the third fails. Results older than twice the interval (minimum 120 seconds) are stale and do not vote. A strict majority of configured enabled locations is required; insufficient fresh results show Performance issues without manufacturing healthy uptime or opening an outage incident. The administration location page shows stale/missing counts and each location's last connection. Results are retained two days; jobs are pruned after a day. Size each location for its aggregate check duration: a single every-minute worker can process only one 30-second check per run under the conservative reservation. For many slow checks, add independently scheduled workers using the same location credential (claims are serialized in the hub), increase check intervals so samples remain fresh, or split checks across locations. Fair rotation prevents starvation but cannot create throughput or guarantee every assignment meets its freshness deadline. Concurrent worker capacity at production scale has not been load tested.

## Alertmanager and Grafana

Prometheus Alertmanager and Grafana alerting can set component status directly, like the Uptime Kuma receiver. Point a webhook receiver at `POST /api/v1/alertmanager` (Alertmanager webhook version 4) or `POST /api/v1/grafana` (Grafana unified alerting webhook contact point), and send a write API token of the page as `Authorization: Bearer <token>`. For another page use `/api/v1/pages/{slug}/alertmanager` with a token of that page. Both share the Kuma receiver's token check, rate limit (60 writes a minute) and 256 KiB body limit, and mark the component as reported from outside by that token.

Each alert names its component with the label `pharos_component`: the component id, or its exact name, on the page of the token. A firing alert with `severity="warning"` sets Partial outage, `severity="info"` Degraded performance, and `critical` or any other severity Major outage. A resolved alert sets Operational. When one notification carries several alerts for the same component, the worst one wins. Alerts without the label, for an unknown component, or for a component with its own enabled check change nothing and are listed under `ignored` in the JSON answer, with the reason. Like the Kuma receiver, these endpoints change status only; they do not open or close incidents.

## Web scheduler

Ordinary hosting cron remains preferred: `php artisan schedule:run` every minute. A global administrator can enable the external fallback on Scheduler and backups after configuring a random token of at least 32 characters as `PHAROS_WEB_CRON_TOKEN` in the private environment. Both `POST /api/cron` and `GET /cron/run` accept an `Authorization: Bearer <credential>` header. URL-only cron services must support configuring that header. Query-string credentials are deliberately rejected because web servers and external services often retain URLs in access logs. The UI never displays the token. The fallback uses constant-time authentication, rate limits and a shared five-minute scheduler lock; scheduled jobs retain their existing overlap locks. Disable the fallback or rotate the environment token to revoke access.

## Remote backups

Only installation administrators can add, run or remove destinations. S3 credentials and SFTP passwords are encrypted using Laravel's application key and never redisplayed, serialized or flashed after validation. S3 requires HTTPS, uses private objects and SigV4 authentication, and resolves/vets/pins the destination for every request including streamed reads. Redirects and TLS verification overrides are prohibited. For an intentionally private storage endpoint the administrator must select Allow this destination on a private network. Since 1.2.0 carrier grade NAT and Tailscale (100.64.0.0/10), benchmarking, the IETF block and multicast count as private too, and IPv4 inside NAT64 or 6to4 is judged as that IPv4 address; destinations that already used such an address were given the private network permission during the update. Loopback, this machine and metadata/link-local addresses remain prohibited. SFTP pins the vetted address and requires a complete verified SHA256 or SHA512 SSH host fingerprint (OpenSSH SHA256 form, raw or colon-delimited hexadecimal, and base64 are supported). Invalid or missing persisted fingerprints fail closed before a connection. Verify that fingerprint through a trusted channel; do not accept one from an untrusted first connection.

`php artisan pharos:backup-remote` runs daily at 02:45 through the normal scheduler; Back up now performs the same delivery. For SQLite it uses the native SQLite online backup API and checks integrity, including data still in WAL. This requires PHP's sqlite3 and zip extensions. MySQL snapshots use installed `mysqldump --single-transaction --quick`; the credentials travel through a temporary private config file and are removed afterward. Transactional database tables are required for a consistent MySQL dump; the backup path for an external MySQL server has not been acceptance tested yet. Application files, migrations and public uploads are included, and `.env` (APP_KEY) only when the archive is encrypted (see below); dependencies, git data, caches, sessions, logs and older backups are excluded. Each upload is downloaded and SHA256 checked. Verification downloads are capped while transferring at the exact local archive size (including chunked S3 responses), with a shared five-minute delivery budget; S3 requests have a 60-second cap and no automatic retry, while native SFTP operations have at most a 20-second socket timeout and byte/deadline callbacks. Invalid HTTPS endpoints containing userinfo or query/fragment data are rejected and never flashed into forms. Status records the last attempt, success and a generic failure message. Local temporary archives are deleted in all delivery paths. Configure destination lifecycle/retention separately; Pharos does not delete remote historical backups.

### Backup passphrase

On **Scheduler and backups** an installation administrator can set a **backup passphrase** (at least 12 characters). With one, every remote archive is encrypted before upload and named `pharos-….zip.enc`:

- The key is derived from the passphrase with Argon2id (libsodium `crypto_pwhash`, three passes over 64 MiB, a random 16 byte salt); the archive is encrypted in 1 MiB chunks with libsodium secretstream (XChaCha20 Poly1305), so changed, reordered, cut or extended files are refused. A small header holds the format version, the Argon2id cost and the salt, and is authenticated with every chunk.
- Encrypted archives include `.env` with APP_KEY, so one archive is a complete restore.
- The passphrase is stored on the server encrypted with APP_KEY, because the nightly upload runs without anyone to type it. That protects the bucket, not the server. Keep a copy of the passphrase somewhere else: without it an archive cannot be opened, and nobody can recover it for you.
- If the stored passphrase can no longer be read (APP_KEY changed), the backup stops with an error instead of uploading an unencrypted archive. Set it again.

Without a passphrase the archive is a plain zip and **leaves `.env` out**, so whoever reads the bucket does not get APP_KEY. The screen then warns to keep APP_KEY somewhere else: without it the encrypted fields in a restored database (two factor secrets, mail and backup credentials) cannot be read.

Open an encrypted archive on any machine with Pharos and PHP sodium (no database needed):

```
php artisan pharos:backup:decrypt pharos-20261120-024500-0123456789abcdef.zip.enc [--out=restore.zip]
```

It asks for the passphrase, refuses to overwrite a file, and writes nothing when the passphrase is wrong or the file is damaged. Archives made before a passphrase was set, or after it was removed, stay plain zips. Local backups made by the updater (Updates screen) are unchanged.

The archive contains account data and credentials: keep storage private. To restore, stop writes, decrypt the archive if it ends in `.enc`, restore files and `.env` (from the archive, or from your own copy when the archive has none), restore `database/database.sqlite` or import `database/database.sql`, reinstall dependencies from `composer.lock`, create writable storage/cache directories and restart the scheduler. Shared-hosting installations with a separate public directory back up the actual configured public_path under one public/ archive prefix; stale base/public files are excluded. BACKUP-LAYOUT.json records the source mapping. Restore public/ into the current configured document root, not blindly into the application tree; rebuild the storage symlink and adjust .pharos-public if moving hosts. Public .env files and symlinks are excluded. Preserve the original APP_KEY; it decrypts stored destination credentials and TOTP secrets.

## Passkeys

Registration, list and password-confirmed removal are available on Your profile. Sign in with a passkey uses a discoverable credential, so it does not ask for an email or disclose whether an account exists. Registration requires the current account password. Device verification and user presence are required; the maintained `lbuchs/webauthn` library checks challenge, RP hash, origin, signatures and signature counters. Pharos additionally checks the exact configured origin (including scheme/port), rejects cross-origin ceremonies, binds the returned user handle to the credential's account and atomically consumes an expiring database challenge. Existing enabled TOTP remains a separate required sign-in step; passkeys do not satisfy or disable an administrator's TOTP enrollment requirement.

Configure `PHAROS_WEBAUTHN_ORIGIN` to the exact administrator HTTPS origin, defaulting to APP_URL. RP ID is its hostname. HTTPS with a hostname is required outside localhost. IP origins are not valid WebAuthn RP IDs (W3C §5.1.3/§5.1.4 allow only the domain form of host); an HTTPS IP address alone is insufficient. An installation reached over plain HTTP or by IP address keeps password sign in, but cannot register or use passkeys: give the administrator origin an HTTPS hostname with a trusted certificate, for example `https://status.example.com`, and set APP_URL to that administrator origin because central administration deliberately rejects other hosts. A Chromium insecure-origin-as-secure override alone does not bypass the server's HTTPS origin verification. Changing the RP hostname requires registering credentials for the new RP. Backup your existing account recovery path before removing a device.
